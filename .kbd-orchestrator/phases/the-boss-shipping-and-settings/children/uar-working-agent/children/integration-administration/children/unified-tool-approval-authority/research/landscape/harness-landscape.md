# Harness approval/execution landscape

Accessed: **2026-09-24**. Scope: Codex (local Rust core and app-server), Claude Code / Claude Agent SDK, OpenCode, Gemini CLI, and official DeepSeek Harness. Research only; no implementation, build, or behavioral test was run. Findings describe current upstream docs and source snapshots, not the versions bundled by The Boss. Codex source findings are integrated below; the companion assessment maps them to the active UAR/Boss worktrees.

## Result

The common pattern is **runtime-owned execution with a suspended approval continuation**. This does **not** establish that a UI must be a passive yes/no renderer: Claude's public SDK explicitly permits replacement input and permission updates; Gemini supports edited content and policy changes. OpenCode and DeepSeek provide useful examples of narrower one-shot reply contracts.

Approval policy, one-shot user consent, sandbox enforcement, UI presentation, and crash recovery are distinct responsibilities. The sources do not justify collapsing all of them into a single generic boolean, nor do they prove that introducing a new central subsystem is necessary for this project.

## Codex: directly applicable Rust execution and approval reference

Codex is the closest implementation reference for UAR because its core and app-server are written in Rust and their source is available locally. This is an architectural fit judgment, not a claim of overall superiority or drop-in compatibility.

**Coordinator with independent enforcement.** Session::request_approval routes hooks, Guardian or user review. Exec can reject a forbidden action before that router, and enabled controller proxies remain independently authoritative. MCP configuration can disable a tool before consent is requested. One coordinator therefore does not mean one permissive boolean overriding all policy. [Approval router](/Users/gqadonis/Projects/references/codex/codex-rs/core/src/tools/approvals.rs:495), [execution orchestrator](/Users/gqadonis/Projects/references/codex/codex-rs/core/src/tools/orchestrator.rs:125), [MCP restrictions](/Users/gqadonis/Projects/references/codex/codex-rs/core/src/mcp_tool_call.rs:205).

**Execution stays attached to the approved request.** The orchestrator awaits approval and then executes the same request through sandbox selection. PreparedMcpCall holds client, immutable configuration, tool/server metadata and catalog revision. Its execution path rejects stale catalog state and holds a catalog lease. This is the useful pattern for replacing Boss's tool-plus-arguments FIFO with a prepared, identity-bound operation. [Await then dispatch](/Users/gqadonis/Projects/references/codex/codex-rs/core/src/tools/orchestrator.rs:208), [prepared MCP binding](/Users/gqadonis/Projects/references/codex/codex-rs/codex-mcp/src/binding.rs:169), [revision/lease checks](/Users/gqadonis/Projects/references/codex/codex-rs/codex-mcp/src/binding.rs:305).

**Register before emit; consume once.** Core registers the waiter using approval_id when present, otherwise call_id, before emitting the request. Resolution removes the waiter. App-server uses a separate JSON-RPC request ID while retaining its mapping to the original approval. It can send the same request to multiple connections; removal gives first-response-wins for that live waiter. [core pending identity](/Users/gqadonis/Projects/references/codex/codex-rs/core/src/session/mod.rs:2637), [core resolution](/Users/gqadonis/Projects/references/codex/codex-rs/core/src/session/mod.rs:3203), [transport mapping](/Users/gqadonis/Projects/references/codex/codex-rs/app-server/src/bespoke_event_handling.rs:907), [transport resolution](/Users/gqadonis/Projects/references/codex/codex-rs/app-server/src/outgoing_message.rs:457).

**Reconnect is not process resurrection.** App-server retains original serialized requests and can replay still-live pending requests to a connection during running-thread resume. Core turn waiters and app-server callbacks are memory maps; inspected source does not establish durable reconstruction after process death or exactly-once external writes. [pending transport map](/Users/gqadonis/Projects/references/codex/codex-rs/app-server/src/outgoing_message.rs:104), [replay](/Users/gqadonis/Projects/references/codex/codex-rs/app-server/src/outgoing_message.rs:362), [resume wiring](/Users/gqadonis/Projects/references/codex/codex-rs/app-server/src/request_processors/thread_lifecycle.rs:791), [core waiter storage](/Users/gqadonis/Projects/references/codex/codex-rs/core/src/state/turn.rs:88).

**Do not over-copy the reference.** Approval metadata is for routing/presentation, not an independently verifiable execution receipt. Hosted-file argument rewriting can occur after logical approval; exact wire-argument equality needs an explicit Boss/UAR contract. Session/persisted approval rules can intentionally authorize broader future calls, and are distinct from durable pending decisions. [argument rewriting](/Users/gqadonis/Projects/references/codex/codex-rs/core/src/mcp_tool_call.rs:455), [remembered approval scope](/Users/gqadonis/Projects/references/codex/codex-rs/core/src/mcp_tool_call.rs:1628), [persistence](/Users/gqadonis/Projects/references/codex/codex-rs/core/src/mcp_tool_call.rs:2142).

| Codex mechanism | Apply to UAR/Boss | Remaining local work |
|---|---|---|
| Rust coordinator awaits approval then dispatches prepared operation | Retain UAR orchestration and existing root/child broker | Stop Boss auto-policy from weakening UAR Ask |
| Prepared MCP binding + catalog revision lease | Bind authorization to the resolved tool/server/revision and invocation | Carry authenticated identity across the UAR-to-Boss process boundary |
| Separate approval and transport IDs, register-before-emit | Preserve runtime identity through UI and transport adapters | Remove tool/args-only FIFO consumption; distinguish child execution identity |
| Single-consumption callbacks + replay of live pending requests | Reuse pending record on renderer/SSE reconnect | Explicit duplicate, cancellation and generation outcomes |
| Independent sandbox/controller restrictions | Boss remains authoritative over capabilities it owns | Compose restrictions monotonically rather than overriding required consent |

**Build versus adopt:** reference and adapt these patterns inside existing UAR modules. Importing the Codex runtime or replacing UAR wholesale would add an unassessed dependency and discard existing catalog, AG-UI and administration contracts. Codex supplies a concrete Rust model for the local lifecycle; it does not supply the missing distributed Boss admission contract ready-made.

## Claude: useful adapter seam, not a universal policy intercept

**Verified contract.** `canUseTool` handles calls that fall through earlier permissions. Preapproved tools can bypass it. The docs recommend `PreToolUse` when a check must cover every tool call, and describe deny/ask rules that remain relevant even with hook allows and bypass mode. Do not claim that adding a central callback automatically centralizes all authorization. [Permission evaluation](https://code.claude.com/docs/en/agent-sdk/permissions)

**Verified input/policy authority.** An allow result can carry `updatedInput` and `updatedPermissions`; permission updates can target session, user, project or local settings. The documented “always” example filters suggestions to localSettings, causing a persistent rule. A deny can return a model-visible reason; `interrupt` requests stopping the current turn. The callback can therefore be an active host decision boundary, while execution stays in the engine. [Input handling](https://code.claude.com/docs/en/agent-sdk/user-input), [TypeScript reference](https://code.claude.com/docs/en/agent-sdk/typescript#permissionresult)

**Verified open-source transport, limited engine claim.** Python `_spawn_control_request_handler` records tasks in `_inflight_requests[request_id]`; `control_cancel_request` cancels that task. The can_use_tool handler awaits the host callback, serializes updatedInput/updatedPermissions and sends the correlated response. This proves wrapper behavior, not hidden engine map layout, dispatch internals, or restart guarantees. The wrapper currently creates `ToolPermissionContext(signal=None)`; do not copy TypeScript AbortSignal expectations into Python without checking the shipped version. [query.py, lines 323–372 and 495–552](https://github.com/anthropics/claude-agent-sdk-python/blob/588905686e40dffa32e2f889ce7164df01ff7c8b/src/claude_agent_sdk/_internal/query.py#L323)

**Restart distinction.** SDK sessions store conversation and support resume after restart. The guide separately says permission prompts are handled within a query loop. This does not promise that an old pending approval ID can be answered after a new process starts. A wrapper can persist its own UX record, but treating it as executable authorization after restart requires an explicit runtime reconciliation protocol. The latter is an adoption requirement/inference, not an SDK guarantee. [Sessions](https://code.claude.com/docs/en/agent-sdk/sessions)

**Tradeoff.** Native callback adaptation is small and retains engine semantics. Uniform interception may require hooks, and rewritten arguments make the displayed proposal/approved proposal relationship a real design decision.

## OpenCode: narrow replies and runtime continuations, with a V1/V2 trap

**Verified V2 ownership.** `PermissionV2` stores pending requests in a location-scoped map with Deferred continuations. `assert` evaluates rules, creates a request, publishes Asked, and awaits the Deferred. Its cleanup removes the request when the wait ends. Runtime teardown fails pending waiters and clears the map. Reply looks up the request ID; unknown IDs return NotFound. [Core permission.ts](https://github.com/anomalyco/opencode/blob/6df0d5d951e0bb8c82dd1a7f9315eff4efd7f1ef/packages/core/src/permission.ts)

**Verified reply authority.** HTTP session reply checks that the request belongs to the addressed session. The payload is reply plus optional rejection message; it does not accept replacement arguments. The server uses its stored request's suggested patterns for “always,” not patterns sent in the reply. Listing pending requests offers the building block for reconnect recovery while the runtime survives. These are interface properties, not proof that all network authentication/authorization is correct; this was not a server security audit. [Handlers](https://github.com/anomalyco/opencode/blob/6df0d5d951e0bb8c82dd1a7f9315eff4efd7f1ef/packages/server/src/handlers/permission.ts)

**Verified dispatch.** The V2 edit tool resolves the target, asserts external-directory permission when needed, then asserts edit permission before reading/mutating file contents. The original execution fiber continues after approval; the client does not resubmit a tool body. Source message/call IDs are passed with the permission request. [edit.ts](https://github.com/anomalyco/opencode/blob/6df0d5d951e0bb8c82dd1a7f9315eff4efd7f1ef/packages/core/src/tool/edit.ts)

**Verified sticky scope.** V2 “always” saves project ID + action + resource into a SQLite permission table, and saved allowances do not override configured deny. It may settle other currently pending requests whose resources become allowed, even across sessions within the location service. Reject settles other pending requests in the same session. These are deliberate broadening/cancellation scopes that an adapter should preserve or expose explicitly. [Saved service](https://github.com/anomalyco/opencode/blob/6df0d5d951e0bb8c82dd1a7f9315eff4efd7f1ef/packages/core/src/permission/saved.ts), [SQL](https://github.com/anomalyco/opencode/blob/6df0d5d951e0bb8c82dd1a7f9315eff4efd7f1ef/packages/core/src/permission/sql.ts), [Core](https://github.com/anomalyco/opencode/blob/6df0d5d951e0bb8c82dd1a7f9315eff4efd7f1ef/packages/core/src/permission.ts)

**Do not blend V1 and V2.** Legacy docs say “always” lasts for the current OpenCode session. The inspected legacy implementation holds approved rules in instance state, not durable storage; its exact state lifetime is more precise than that shorthand. V2 docs explicitly say durable project-scoped rules. Context7 returned examples from both generations; source and version labels resolve the apparent contradiction. [Legacy docs](https://opencode.ai/docs/permissions/), [Legacy implementation](https://github.com/anomalyco/opencode/blob/6df0d5d951e0bb8c82dd1a7f9315eff4efd7f1ef/packages/opencode/src/permission/index.ts), [V2 docs](https://opencode.ai/v2/docs/permissions)

**Tradeoff.** This is a strong model for a bounded approve/reject adapter: the runtime retains arguments, identity and continuation. It also shows that durable sticky policy and durable pending execution are separate systems.

## Gemini CLI: scheduler state machine with editable confirmation

**Verified sequence.** `_processToolCall` applies BeforeTool hooks, checks PolicyEngine, awaits confirmation if required, applies policy updates and marks the call Scheduled. `_execute` checks cancellation, marks Executing and calls the executor. The request callId is retained through those states; confirmation uses a separate correlationId. [scheduler.ts, lines 612–759](https://github.com/google-gemini/gemini-cli/blob/a3d69c14200ab65d0f66f703a6c60ad644647138/packages/core/src/scheduler/scheduler.ts#L612)

**Verified mutation authority.** Confirmation can open an external editor and loop with the new diff, or accept inline newContent. The runtime rebuilds invocation arguments through the modifier and updates scheduler state. This is an explicit counterexample to a claim that a sound approval architecture must prohibit all UI-originated input changes. It does not prove that arbitrary caller-supplied args are safe; the supported editing path is specific. [confirmation.ts](https://github.com/google-gemini/gemini-cli/blob/a3d69c14200ab65d0f66f703a6c60ad644647138/packages/core/src/scheduler/confirmation.ts), [tool-modifier.ts](https://github.com/google-gemini/gemini-cli/blob/a3d69c14200ab65d0f66f703a6c60ad644647138/packages/core/src/scheduler/tool-modifier.ts)

**Verified policy breadth.** “Always” options can mean one tool, all tools from an MCP server, persistence to workspace/user policies, or a transition to AUTO_EDIT for edit tools. Mode-scoped allowances apply to the current mode and more permissive modes. A generic “remember” flag would conceal materially different authority changes. Client-initiated tool calls can also turn ASK_USER into ALLOW, except additional-permissions requests; this is another reason to inspect every invocation path before asserting one universal prompt gate. [policy.ts](https://github.com/google-gemini/gemini-cli/blob/a3d69c14200ab65d0f66f703a6c60ad644647138/packages/core/src/scheduler/policy.ts)

**Verified cancellation, limited recovery.** Confirmation listens for the matching correlationId with AbortSignal; it races IDE and bus outcomes and cleans up the losing listener. The source explicitly calls out lost-connection/zombie-listener lifecycle responsibility. Cancel marks the call Cancelled and cancels the queued batch. Resume UI reloads conversation history, working directories and chat; it does not reconstruct the confirmation listener in the inspected path. No claim of crash-safe pending approval recovery is supported. [confirmation.ts](https://github.com/google-gemini/gemini-cli/blob/a3d69c14200ab65d0f66f703a6c60ad644647138/packages/core/src/scheduler/confirmation.ts), [resume hook](https://github.com/google-gemini/gemini-cli/blob/a3d69c14200ab65d0f66f703a6c60ad644647138/packages/cli/src/ui/hooks/useSessionResume.ts)

**Tradeoff.** An explicit scheduler state model makes execution status inspectable and supports rich approval UX. Adopting its full feature set would add argument-editing and policy-scope complexity that may be unnecessary for a narrow unification task.

## DeepSeek: official harness exists; do not conflate it with the model API

The official [DeepSeek Harness developer-preview page](https://www.deepseek.com/harness/en/) links the public deepseek-ai repository and identifies models, tools, sessions, sandboxes and UI as composable plugins. This is an identifiable first-party harness as of the access date. A claim that DeepSeek has no official harness would now be false. Model function-calling support alone says nothing about this harness's permission implementation.

**Verified division of authority.** Tools runs a pre-execute waterfall; ask delegates to ApprovalService; an allowed outcome still passes monotonic guards and cancellation checks before returning dispatch. ApprovalService enforces ask/never before answerer dispatch. Missing/throwing/invalid answerers produce unavailable; only allowed-once grants. This separates the tool execution policy from the human/machine answer channel. [Tools preparation, lines 1493–1537](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/core/tools/src/index.ts#L1493), [Approval service](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/interaction/user-approval/src/index.ts)

**Verified identity and read-only question.** ApprovalService creates a fresh audit ID and records asked/decided. The request carries agent and optional callId, deliberately omitting args; UI references the streamed call. Tools snapshots and freezes execution arguments before the policy stage. Audit ID, tool-call ID and gateway transport ID serve different purposes and must not be treated as interchangeable. [Approval documentation](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/docs/subsystems/approval.md), [Tools snapshot, lines 1391–1452](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/core/tools/src/index.ts#L1391)

**Verified reconnect building block.** Gateway stores remote waterfall continuations in pendingRemoteEvents, delivers live entries when a new client connects, and matches reply eventId to a recorded client delivery. Settlement removes the pending entry, resolves the original continuation and sends cancellation frames to other deliveries. Late/duplicate replies or replies from superseded deliveries are no-ops. Disconnect removes deliveries but leaves unresolved events available for later clients. The approval browser plugin consumes the scoped approval/request waterfall and resolves its presentation promise with a one-shot outcome. [Gateway, lines 491–660](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/api/gateway/src/index.ts#L491), [Browser answerer](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/client/ui-approval/src/client/index.ts), [Remote assembly](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/api/remotes/src/index.ts)

**Verified cancellation and limited durability.** Abort resolves the request cancelled and discards a late answer; the tools layer refuses dispatch on cancellation. Approval policy is an event-folded session override. Approval audit events require an open turn because replay uses a committed turn boundary; the source explicitly warns that bare events outside that boundary can be discarded as crash tail. The gateway continuation map is memory, and its shutdown cancels pending events. A durable audit log is therefore not evidence that the original tool continuation survives process death. [Approval service](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/interaction/user-approval/src/index.ts), [Gateway](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/api/gateway/src/index.ts)

**Verified sticky choice separation.** One-shot UI allows/rejects; separate permission presets combine sandbox mode and approval policy and persist those choices in session events. “never” means reject operations that ask, not a global deny-all. The default full-access preset can combine a broad sandbox with never prompting; capability and consent policy must be read together. [Permission presets](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/docs/subsystems/permission-presets.md)

**Tradeoff.** Separating immutable execution from a small approval question and distinct transport identity is reusable. Adopting Cordis/plugin architecture wholesale would be an unjustified rewrite. Developer-preview source warrants careful version pinning.

## Bounded options for local assessment

These are candidate designs, not an approved architecture or claims about local defects.

| Option | What changes | Benefit | Cost / suitability boundary |
|---|---|---|---|
| A. Preserve each runtime's gate; normalize only presentation and routing | Adapter maps native approval ID + tool-call/session identity to a shared UI record and sends native outcomes back. Runtime retains its pending tool continuation. | Smallest scope; matches the inspected execution-ownership patterns. | Must expose real capabilities and sticky scopes per adapter; “one prompt vocabulary” does not mean one universal policy implementation. Appropriate if observed problem is duplicate/misrouted UI or argument echoing. |
| B. Runtime-owned approval broker for UAR-owned tools, native adapters for external engines | UAR's own execution path asks a central service; third-party engines continue through their native approval callbacks/hooks. UI replies by ID with allowed outcome and explicit policy scope. | Consistent UAR ownership without pretending a callback intercepts every external-engine tool. | Requires tracing actual tool paths and authority precedence; external sandbox/admin policy remains an independent deny boundary. Appropriate if observed problem is divergent UAR tool gates. |
| C. Add explicit durable approval lifecycle only if restart recovery is required | Persist proposal identity, selected policy revision and approval state; reconcile stale pending executions on restart before they can run. | Makes a promised crash/reconnect behavior reviewable. | Largest scope; a log plus ID does not resurrect a process continuation or guarantee exactly-once side effects. Sources above provide no shortcut that proves such semantics. Reject as speculative if the user requires only live-process UI reconnect. |
| D. Deliberately support approval-time edits | Explicit replacement-input operation reconstructs the runtime call and produces an auditable approved proposal. | Claude/Gemini demonstrate legitimate uses such as constrained command or diff editing. | Changes what consent authorizes; must specify display, validation and any re-evaluation behavior. Do not slip arbitrary argument echoing into a boolean reply. Unnecessary if the product does not offer editing. |

Recommended order: evaluate **A**, then **B** only where local evidence requires it; treat **C** and **D** as separate, explicit product requirements. The evidence supports runtime ownership of dispatch, but does not by itself choose a local subsystem split.

## Adversarial questions for the combined assessment

1. Does “unified authority” mean uniform UI, policy evaluation, sandbox enforcement, or execution ownership? Which observed failure requires each?
2. Is a callback actually on every execution path? Claude preapprovals and Gemini client-initiated calls are concrete counterexamples to that assumption.
3. Can one physical tool action raise multiple approval requests (external path, shell expansion, tool policy)? Tool call ID alone need not identify a particular decision.
4. Does “always” mean this process, session, project, mode, tool, server, path or user settings? The surveyed systems disagree.
5. Is the approved object the proposal shown to the user, or an edited replacement? Claude/Gemini make replacement legitimate but explicit.
6. Can a UI disconnect while the runtime keeps waiting? Does process death terminate the continuation? Do not claim restart safety based on a history log.
7. What should happen to another pending request when one is rejected or always-approved? OpenCode and Gemini have batch/session effects that a generic broker could accidentally erase.
8. Does a persistent rule revoke or override an explicit configured deny? OpenCode V2 preserves deny; “last matching wins” alone is an incomplete description of the combined policy.
9. Who reconciles stale answers, canceled requests and updated runtime generations? DeepSeek illustrates transport delivery identity in addition to tool identity.
10. Have the exact installed versions been inspected? Current docs and current main branches cannot prove a bundled older SDK's behavior.
