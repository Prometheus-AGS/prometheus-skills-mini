## A4: five finite real desktop negative cases

Use the ordinary production-feature artifact, the actual Electron app/IPC/stores, existing selected deferred server/catalog and normal 32/8/512 caps, actual UAR loop, and existing private HTTP model provider and SDK MCP receiver. Give each case its own real session. There is no direct call to the fixture validator as standalone completion evidence. Each proposed fault is activated only by a genuine authenticated incoming model request from that actual run.

For the first four cases, issue exactly one normal discovery proposal through the existing ProjectionProviderConversation. Approve its actual exact approval ID through runTurn's ordinary API. On the second genuine provider HTTP request, first verify in memory that the unmodified request has exactly the issued current-turn assistant call, one corresponding real tool result and the expected actual later target advertisement. These are strict fixture preconditions; if absent, fail the setup rather than mutate a guessed object. Clone only that in-memory provider input, apply exactly one listed mutation, and call the real conversation validator once on that input. Never alter UAR persisted history, its actual advertised catalog, admission metadata, approvals, wire protocol or executor. The fixture's existing HTTP400 failure response returns to the genuine sidecar and must produce an actual failed run/stream observation.

The filler receiver already increments its filler-call counter and throws before its target effect handler (toolServer: non-read_projection branch). That counter is a dispatch count, not a successful business effect. The receipt must say fillerDispatches1 and protectedTargetEffects0, not claim no dispatch occurred. Native discovery in the first four cases really executes once; zero effects refers to the protected MCP target, not zero activity in the whole run.

The first four cases certify the **controlled-provider correlation/refusal boundary on real incoming UAR traffic**, not UAR robustness to malicious history that UAR itself generated or accepted. The fifth additionally exercises actual receiving MCP refusal. The transport mutation is explicitly part of the fixture, not a reproduced product defect. No generic model robustness, visibility bypass, remote receiver security or arbitrary native implementation claim follows.

Choose the filler-dispatch alternative explicitly allowed by A4's “or duplicate target proposal.” A deliberately executed duplicate-target-proposal case remains unrun; do not mark its static guard separately reproduced. In the current state machine the completed-conversation guard is reachable only after an already successful target call; a true later duplicate attempt can establish zero **additional** target effects, not zero total effects. Duplicating an advertised schema instead hits invalid_request_shape and is not a duplicate-proposal test. Do not substitute either claim silently. If root interprets the requirement as both alternatives mandatory, record that separate case/zero-additional-effect contract before authoring it; this proposal does not invent a product rejection behavior for a legitimately new approved invocation.

## Finite receipts and mandatory lifecycle

Per case include version, category, boundary ('authenticated_host_claim' / 'provider_input_fixture' / 'receiving_mcp_refusal'), status, stage, originalPreconditionsMatched, faultAppliedOnce, actualProviderRequests, actualProviderHttpStatus, expectedFailureCategoryMatched, discovery/target/filler proposal/preparation/exact-decision counts, sourceRevisionMatches, protectedTargetEffects delta, fillerDispatches delta, actualRunFailureObserved, noInventedCompletion and cleanupConfirmed. Host case instead carries actual refusal status, authorized-state comparisons and acknowledged consume/effect counts. Only include applicable fields; do not disguise unavailable observations as zero.

Use actual counters and booleans; no body, error string, credentials, canaries, owner/call/session IDs, target names, endpoint or stack output. Preconditions, mismatch, missing expected provider failure, extra request/proposal, unexpected effect, operational error or missing cleanup all fail. Preserve partial completed outcomes in the outer failure JSON. Abort any still-active actual run through its existing owner-bound IPC route, close/warm-session and inspect persistence through current app facilities, restore the capture/negative selector, and leave the app/provider/receiver lifetime with their existing owner. Missing or interrupted expected run termination is not a successful negative.
